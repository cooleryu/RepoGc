# Decision 0004: Phase 0.7 liveness evidence and review workflow

- Status: Accepted
- Date: 2026-09-02
- Approval: `[human-approved 2026-09-02]`
- Change class: C — report schema and finding explanation semantics

## Context

A broken path, missing inbound reference, old Git touch, or unreachable graph node
cannot establish that an artifact has no value. The August 2026 process-log
incident showed that a rarely read file may still be required by a SKILL, gate,
machine consumer, or audit workflow.

Phase 0.5 added typed static edges and configured-root reachability. Phase 0.6
added lexical context for unfinished markers. Those mechanisms still left the
reviewer to join graph, Git, coverage, and known-unknown evidence manually.
The existing `explain` command only printed raw finding JSON, and there was no
standalone read-only `diff` command.

## Decision

RepoGC report Schema 0.4 adds an `artifact_liveness` collection for artifacts
that are subjects of a Finding. Each profile keeps the following dimensions
separate:

- human-declared root;
- reachability from configured roots;
- static inbound references;
- contract or instruction consumers;
- build, test, CI, state, or configuration consumers;
- Git last-touch availability;
- dynamic consumers;
- external-system consumers;
- runtime access;
- business meaning.

Dimension states have bounded meanings:

- `OBSERVED`: the configured mechanical surface produced evidence;
- `NOT_OBSERVED`: the configured mechanical surface did not produce evidence;
- `UNKNOWN`: RepoGC did not inspect that surface;
- `NOT_INFERRED`: the project constitution forbids that inference;
- `NOT_APPLICABLE`: the dimension cannot apply, such as reachability for a
  missing target.

`NOT_OBSERVED` is never rewritten as “absent”, “unused”, or “safe to remove”.
No score or deletion probability is produced.

`repogc explain FINDING_ID` now renders the mechanical Finding, its trend state,
the associated liveness profiles, limitations, human-review guidance, and the
verdict boundary. `--json` provides a structured form.

`repogc diff` independently compares an existing report with the formal
baseline without scanning or writing. It lists new and resolved Finding
identities and preserves basis-change warnings. `--json` provides a structured
form.

## Migration

- Report Schema changes from `0.3` to `0.4`.
- Finding ID generation and ordering do not change.
- Mechanical detector categories do not change.
- A scan against a Schema 0.3 baseline must report a basis change.
- After review, the formal baseline is migrated explicitly with
  `repogc baseline --update`.

## Safety and limitations

- Liveness profiles are produced only for Finding subjects, not every artifact.
- Profiles reuse already collected static evidence and do not execute target
  repository code.
- No network, runtime, external-system, or human-activity collection is added.
- Git last touch remains background evidence and never becomes a verdict.
- AI annotation remains unimplemented and cannot alter these profiles.

## Verification

- A SKILL-only consumer must be shown as observed contract evidence.
- Dynamic consumers and runtime access must remain explicitly `UNKNOWN`.
- A missing target must distinguish observed inbound reference evidence from
  non-applicable reachability.
- `explain` must expose unknowns and the verdict boundary.
- `diff` must not modify the report or baseline.
- Historical C1-C6 and graph/marker sentinels must continue to pass.
- RepoGC and the Best Runtime Box corpus must be scanned with the new report.

## Rollback

Revert the Phase 0.7 implementation commit and then explicitly restore or
rebuild the previous Schema 0.3 baseline. Do not compare Schema 0.3 and 0.4
counts as repository-quality change.
