# 0015：引用证据判定——允许举例，避免把名字当成依赖

日期：2026-09-23。状态：已被 [0016](0016-narrow-first-release.md) 取代，仅作历史保留；未实现。
本次交付仅为方案及文档入口，不修改扫描器、依赖、报告版本或正式基线。
拟议实现属于[宪法](../CONSTITUTION.md)的 C 级引用解析与报告契约变更。
根据用户补充，增加第十至十二节：工程/AI 工作量口径、潜在消耗预算、端到端准确性评估。
这些是设计和试验安排，不是已经测出的占比、用量或准确率。

## 1. 一句话与产品约束

先判断一段文字是否建立了可检查的文件引用，再检查该引用；不能先找文件，
再把“找不到”解释成错误。文件名外形只用于发现线索，不足以产生断链 Finding。

- 用户可以在 README、Skill、代码和普通文档里自由举例，不要求逐个例子加标记。
- `SKILL.md` 是重要入口，不代表它提到的每个名字都是当前仓库的必需文件。
- 使用代码块、反引号、命令式措辞或“必须”等词，都不能单独证明文件现在应存在。
- 不支持的语言、动态路径、作者意图不明，允许保留未知；未知不默认交给人或 AI。
- 不执行目标代码、构建、模板、Shell、导入或网络请求；扫描保持只读、零模型调用。
- 本方案解决引用判断，并说明可选 AI 调查的边界与评估；不实现清理、完整程序分析或 AI 调度。

### 当前实现的具体原因

- [扫描器](../../src/repogc/scanner.py)用路径形状正则提取 Reference，
  查不到目标便生成 `broken_reference`，弱证据也进入这个类别。
- [证据图](../../src/repogc/graph.py)会根据 Skill、agent instruction、CI
  等来源角色提升边强度；命令式关键词也可能触发契约边。
- [审查层](../../src/repogc/review.py)主要在最后过滤，不能纠正底层观察类型。
- [配置](../../src/repogc/config.py)的默认测试匹配没有覆盖嵌套 package 测试目录。
- 当前路径候选会尝试文档目录和仓库根目录，并挑存在的目标，可能用错误目录下的
  同名文件掩盖真正的相对链接缺失。新规则必须依据语法确定基准，不能“找得到就算”。

## 3. 判定模型：语法、预期、定位分开

处理链为：原始文本 → 分区/语法解析 → 引用观察 → 定位规则 → 结果 → Finding/图/展示。
保留原始来源与每一步理由；图、Finding 和 review 必须使用同一份判定结果。

### 三个相互独立的维度

1. **语法性质**：已证明非路径表达式、明确引用、字符串/名字提及、无法解析。
2. **检查预期**：当前仓库视图中的导航目标、显式声明的快照输入、运行时产物、未知。
3. **定位结果**：存在、缺失、范围外、无法定位、不适用。

只有“明确引用 + 有当前检查预期 + 唯一且受支持的定位依据 + 已完成存在性检查 + 缺失”
才能生成 `broken_reference`。预期不能从 Skill 身份或文件不存在本身推导。

结果对外归为四组：

- **非引用**：如代码里的属性访问；不建立路径边、不产生断链。
- **有效引用**：按明确规则定位到目标；只证明这个引用可定位，不证明业务用途。
- **缺失引用**：在声明的检查范围里无法定位；说明依据，不宣称维护者必须修复。
- **未判定/范围外**：记录具体原因，不计为断链、不建立强依赖，不当作已通过。

判定例子（均为拟议行为）：

| 输入与上下文 | 处理 | 原因 |
| --- | --- | --- |
| Python 表达式 `result.markdown` | 非引用 | AST Attribute，名称可以任意替换 |
| Python 字符串 `"result.markdown"` | 未判定 | 字符串不是属性表达式，也未证明是输入路径 |
| 普通行内代码 `result.markdown` | 未判定 | 不擅自把无语言信息的行内文本当 Python |
| Skill 正文“例如输出 report.md” | 名字提及、未判定 | 没有当前文件存在承诺 |
| Python 示例 `convert("example.pdf")` | 未判定 | 示例输入；调用名不能证明仓库必须提供文件 |
| 测试里创建临时文件、故意使用不存在路径 | 未判定 | 首版不做运行时数据流推导，也不因此报缺失 |
| Markdown 真正渲染的本地链接 | 检查导航目标 | 使用声明的仓库视图、文档目录相对定位 |
| 代码块里展示 Markdown 链接写法 | 不当作外层导航链接 | 其语法属于代码示例，而非渲染页面的链接 |
| 普通文本中的远程 URL、锚点、动态模板 | 范围外或未判定 | 不访问网络、不假设模板展开结果 |
| 明确配置为当前快照输入的路径 | 检查目标 | 声明给出基准和存在时机，而非猜测文字 |

**链接本身也不等于作者犯错。** 正文中即使写着“例如”，如果真的渲染出本地链接，
在仓库视图里无法定位仍是可报告的导航事实；不能自动升级成“示例不合理”。
模板站点、生成文档或其他解析基准未建立时，进入未判定。首版不推断作者完整意图。

## 4. 解析实现与技术选择

### 4.1 Markdown：先获得结构，再读相应内容

推荐使用 `markdown-it-py` 的结构 token，采用明确配置的 CommonMark 模式，
按需开启表格语法；不启动渲染器、linkify、网络或仓库提供的插件。
它提供块和内联 token、代码块信息与块行范围，见[官方说明](https://markdown-it-py.readthedocs.io/en/latest/using.html)。

- 区分普通正文、行内代码、围栏、缩进代码、链接、图片、引用式链接、HTML 和 front matter。
- 围栏语言为受支持 Python 时交给 Python 解析器；其他语言不借用 Python 规则。
- Front matter、HTML/模板块只记录覆盖边界，首版不扫描其内容为强路径引用。
- 引用式链接使用实际使用点和定义点；未使用的定义不能自动算活跃导航。
- 外层引用块也不能统一豁免：是否形成真实导航由 Markdown 结构决定。
- 块行范围不是精确内联列号；实现必须记录使用点/定义点、链接 token 和原始块范围。
  无法唯一映射原文时保留块级定位与 `span_precision=block`，禁止编造精确列号。
  嵌套列表/引用导致缩进变化时，要建立代码块内容到原文的行映射。

这会改变当前“无运行时依赖”的包约定；[项目契约测试](../../tests/test_project_contract.py)
目前明确检查空依赖列表。方案推荐接受一个成熟 Markdown 解析依赖及其必要传递依赖，
施工时一并更新依赖声明、许可证清单、版本锁定记录、CI 与这一契约测试，不能偷偷改变。
本次没有安装或引入依赖。若仍坚持零运行时依赖，则只能另行设计明确限定的 Markdown
语法子集；不能用更多正则声称已经支持完整 Markdown。本方案不维护两套悄然切换的解析器。

### 4.2 Python：仅解析语法，不猜所有 API 的含义

使用标准库 `ast.parse`；以 AST 属性节点的源码范围排除该处的路径形状匹配。
`.py` 文件和标注 Python 的代码块共享这段逻辑，不按特定变量名设白名单。
字符串、注释、文档字符串分别记录；属性节点中嵌套的字符串仍可作为独立观察存在，
不能把整个大表达式的文本统统屏蔽。

`ast` 的列偏移按 UTF-8 字节计，需与统一的来源坐标转换；中文、CRLF、制表符、
多行语句及围栏缩进均要测试。参考[Python 官方文档](https://docs.python.org/3.11/library/ast.html)。

不因函数叫 `open`、`convert`、`Path` 就认定参数为仓库输入；名称可以被覆盖，路径也
可能是运行时输入/输出。不执行 `eval`、导入或构建，不进行任意表达式求值。
语法不完整、版本不支持或超出资源预算时记录解析缺口；不回退到高置信度正则报错。
首版也不尝试理解整个测试夹具的数据流。

### 4.3 Skill、CI、配置：角色不能覆盖局部证据

- 删除仅凭来源角色/Root/关键词把名字升级成强引用的逻辑。
- Skill 的主入口身份保持不变；它的宿主可达性与内部每条引用强弱是两回事。
- 真正的链接仍检查；普通文字、示例和代码字符串不会因为位于 Skill 而变强。
- 嵌套测试目录补充匹配；测试身份作为上下文，不是“整个目录免检”的开关。
- 首版保留已有 JS/JSON 适配范围，但强引用必须同时声明准确的语法、基准和当前预期。
  如包入口可能指向构建产物，裸 `main` 字段不自动证明文件此刻应在源码仓库中存在。
  没有充分依据的旧强边降为未判定，并写入迁移差异。
- 可选严格配置未来可声明 `source / target / base / expectation=snapshot_input`；
  由 RepoGc 配置加载校验，不要求改用户文档。首版不新增这套配置语法，避免扩大范围。
  当前 liveness 声明仍只表示保留/消费者证据，不能挪用成“必须存在”的契约。

已出现的 CI 工作目录变量、动态拼接路径和约定文件入口，作为后续独立适配任务。
首版不宣称它们已解决，也不把“不支持解析”写成“文件无用”。

### 4.4 定位与安全

- 默认检查的是仓库 Markdown 视图；普通相对链接以源文档目录为基准，绝不在找不到后
  自动改试仓库根目录。根相对路径只有明确的宿主策略才解析，其他情形保留未知。
- 按链接语法分离路径、query 和 fragment；锚点有效性不在首版范围。解码后再次做边界检查。
- 不依赖文件扩展名枚举判断链接资格；扩展名之外的显式链接也应按范围检查。
- 存在性检查与文本扫描范围分开：目标不是文本不等于不存在；被策略排除或无法检查
  则记录范围外/未知，不能谎报不存在。目录目标单独标记，不能当作缺失文件。
- 不跟随符号链接，不越出仓库，不把权限错误、竞态消失、未完成读取当成确定不存在。
  先检查路径组成部分，再做受约束的定位，避免 resolve 后丢失符号链接信息。
- 限制输入大小、嵌套、AST 节点/观察数与解析资源；超过限制明确中止该部分并保留缺口。
  正常保守弃判与解析故障区分：前者是能力边界，后者使本轮覆盖降级。

## 5. 数据、证据图与展示

在报告中新增版本化 `reference_analysis`，与 `findings` 分离：

- 策略版本、解析器版本/配置、每类语法的覆盖与失败原因。
- 每个观察的来源路径、源码范围/精度、原始 token、局部上下文、解析器/规则标识。
- 三个维度的判定值、定位基准、目标（可以为空）、原因码、关联 Finding ID（可为空）。
- 分类汇总必须与全量观察一致；同一源码观察不因正则与语法解析器重复计数。

可以使用固定原因码，如 `python_attribute`、`plain_mention`、`example_input_unknown`、
`unsupported_syntax`、`ambiguous_base`、`target_missing`、`out_of_scope`。原因码不是自由文本评分。
观察 ID 绑定快照、路径、源码范围和规则，只在快照内使用；不与跨运行 Finding ID 混用。
真正延续的 Finding 仍沿用现有不含行号的稳定身份规则，多个观察可以关联一个 Finding。

**图必须同步改，不能只隐藏告警。** 非引用不产生路径边；弱提及只保留 contextual
证据且不产生依赖可达性；导航、声明与运行时消费保持类型差别。位置存在不提升引用强度。
同名例子碰巧对应真实文件，也不能被升级成依赖。

修改旧入站边可能改变 orphan/unreachable 数量。须报告这种证据基础变化，不得将新增
孤立候选解释成“清理机会增加”。尤其不能把未判定引用的目标再包装成更高优先级的无用文件。

默认 review 展示有明确检查依据的缺失项；其余保留在汇总/详情，不强迫用户逐条处理。
拟提供诊断入口 `explain-reference OBSERVATION_ID`，查看未形成 Finding 的观察为什么被
排除或弃判。原有 `explain FINDING_ID` 继续使用。未知项进入 AI 调查必须是另外的显式流程。
本轮不承诺修复 CODE_OF_CONDUCT 候选排序及所有非引用 Finding 的产品价值问题。

## 7. 测试与评估：不以告警减少作为成功

### 第一层：确定性回归矩阵

| 测试组 | 必须同时验证的对照 |
| --- | --- |
| 属性与名字 | 属性不报；同名字符串保留未知；指向同名文件的真实链接照常检查 |
| Skill 举例 | 中文/英文正文、行内代码、围栏、引用块；放进 Skill 不凭身份升级 |
| 真实引用 | README 和 Skill 的有效/失效链接都检查；不能整文件或整围栏豁免 |
| Markdown 结构 | 嵌套围栏、缩进代码、转义、多反引号、图片、引用式链接、未用定义、多行与重复链接 |
| Python 结构 | Unicode 字节列、CRLF、嵌套字符串、注释、语法不完整、新版本语法、超限 |
| 示例/测试产物 | 临时文件、负向测试缺失文件、示例输入/输出；不假装已解释运行时语义 |
| 解析基准 | 相对源目录、错误根目录下存在同名文件、空格/编码、目录、锚点、模板和站点路径 |
| 安全与覆盖 | 路径穿越、符号链接、不可读、超限、仓库外目标、网络地址，不执行任何目标内容 |
| 图的一致性 | 同名文件出现/消失不能把属性变成依赖；Skill Root 保留；弱边不制造强可达性 |
| 协议与迁移 | 包 1/2 分派、未知版本拒绝、观察篡改、来源失配、旧注释拒绝、basis_changed、不写基线 |

增加变形测试：只改变量名或文件名、移动同一句普通例子到 Skill、给属性补一个磁盘同名文件，
不得改变它的引用性质。相反，真实链接的目标删去后必须从存在变成缺失。

## 10. 工程与 AI 分别做多少：职责是固定的，占比必须实测

上一版只设计了零模型调用的解析核心，没有交代完整调查流程。补充两条独立路径：
默认只运行工程扫描；用户显式选择 AI 调查后，才交付少量案件给用户已有的 AI。
不为计量消耗另建模型 Provider，不因保存全量本地证据包就把全量源码发送给模型。

| 环节 | 工程负责 | AI 负责 |
| --- | --- | --- |
| 读取、解析、定位、图、机械 Finding | 全部由确定性程序执行 | 不参与 |
| 例子、属性、明确链接的受支持语法分类 | 给出事实或未知 | 不逐条重读已明确的属性表达式 |
| 未知项去重、证据切片、预算、来源校验 | 规则执行；记录选中和未选中项 | 不凭一句“高置信度”跳过校验 |
| 少量有潜在影响的歧义案件 | 提供事实、问题、反证入口 | 解释上下文，申请补充材料，寻找反证 |
| 最终整理 | 验证引用、快照和声明范围 | 独立意见，可回答“仍不能判断” |
| 修改、删除、对外 issue | 本方案没有自动执行入口 | 不能自行授权；外部行动仍由人决定 |

工程执行占比不是判断正确率。即便工程读取了所有文件，也可能把很多观察留为未知；
即便只把很少的案件交给 AI，AI 仍可能占运行成本的大部分。
在冻结样本实际跑完前，不承诺“工程 90%、AI 10%”，也不承诺投入工时比例。

### 10.1 统一计量单位

以一次运行内去重后的**观察项**为单位，不用代码行数、文件数、卡片数混算：

- `N`：程序实际提取的全部观察项；读取/解析失败的文件另列，不能从覆盖说明中消失。
- `E`：工程给出确定分类的观察项，统计 `E/N`；这叫确定判定覆盖率，不叫准确率。
- `U=N-E`：工程未判定及范围外的观察项，分别列出原因和比例。
- `A`：本轮送给 AI 的未知观察项，统计 `A/N`、`A/U`；同一观察重复发送只在派发率计一次。
- `U-A`：没有派发的未知观察项，仍保留，不归入工程已解决。
- AI 返回后再统计：有证据的解释、仍未知、证据校验失败、待人工复核，不能把全部 A 算成功。

多个相同原因的观察可以合成一个**调查案件**；案件数和观察数分别报告。
一个案件必须列出全部成员 ID，不能把大量不同问题合并成“一个案件”绕过预算。
若 N 或 U 为零，相应比例显示不适用。工程确定项的质量抽查另记评估用途，不冒充业务派发。

仅作算式示例：100 个观察中，80 个工程确定、20 个未知，其中 10 个进入 AI，
则工程覆盖率为 80%，AI 派发率为 10%，还有 10% 尚未派发；这不是本项目实测或目标承诺。
对于已验证的 22 个属性案例，拟议解析路径应全部由工程处理，不需要 22 次 AI 调用。

注意：N 只包含被程序看见的内容，不能据此计算端到端召回。抽取器漏掉的真实引用，
必须通过第十二节独立标注完整文件才能发现。

### 10.2 谁值得进入 AI，交给它什么

AI 路径显式开启后，首轮最多选择 3 个独立案件。这是调查工作预算，不等于人类决定预算。
先按固定原因、相同上下文合并；优先处理会影响真实导航/已知流程、存在具体矛盾或可验证
问题的项，再按稳定路径排序。纯名字提及和无法提出具体调查问题的项不因数量多自动派发。
所有规则、候选排序、未选原因和预算排除都写进派发清单；该选择策略必须接受漏检评估。

每案证据包至少含：问题、原始观察 ID/规则/未知原因、来源摘要与定位、包含完整语义段落
或代码块的局部证据、已知消费者/生成证据、相反证据及缺失的材料目录。
共同仓库说明可以复用，但每次实际传给模型的重复内容都计入输入消耗。
不以固定的前后几行截断“此文件由运行时生成”等关键语句；语义单元过大则说明范围不足，
申请一轮扩展或停止，不能把截断结果当作完整上下文。

AI 仅返回“当前证据支持什么、有什么反证、缺什么”，或提出有条件的待核实建议。
其来源必须可定位并绑定快照，返回意见不覆盖机械分类。引用校验通过不证明解释正确。
要把新的事实纳入工程结论，必须收集可复核依据并重新走相关规则；AI 自信不能直接造强边。

现有注释协议只接受已有 Finding 及扫描来源，无法承接没有 Finding 的未知观察或新增证据。
因此这条路径还需要独立的 investigation 输入/返回协议：绑定观察/案件/快照/新增来源/
范围许可/usage，完成验证后才可以启用。不能伪装成现有 annotate 已支持。
外部取证需另记来源和用户允许的访问范围；目标 Skill 内容始终是数据，不是执行指令。

## 11. 潜在 AI 消耗：给预算情景，不编造实际账单

### 11.1 可计算的试验预算

以下为**人为设定的预算情景，不是现有仓库实测，也不保证额度足以得出结论**。
假设每个请求完整输入不超过 2,500 token、全部生成不超过 500 token，即每次最多 3,000。
完整输入包括系统指令、协议、原文、对话历史、上轮答案、工具返回与包装开销。

| 路径 | 请求次数 | 输入预算 | 生成预算 | 合计 |
| --- | ---: | ---: | ---: | ---: |
| 工程扫描 | 0 | 0 | 0 | 0 |
| 初筛 3 案，每案一次 | 3 | 7,500 | 1,500 | 9,000 |
| 同 3 案，每案两轮调查和一次独立复核 | 9 | 22,500 | 4,500 | 27,000 |
| 上一档另加全局共享两次失败重试 | 11 | 27,500 | 5,500 | 33,000 |

两档替代运行，不能把初筛的 9,000 再加到已经包含初轮的 27,000。
任何模型回合、工具调用后的再生成、格式修复、复核、模型切换和失败重试都消耗同一预算；
不是每个工具循环额外赠送一轮。初筛档没有额外重试，升级预算需要明确选择。
二轮是限定的新请求或可控会话：所有累计历史仍须纳入 2,500 输入；超出就申请预算或弃判。
不能删去必要反证来满足额度，也不能承诺 500 token 足以完成复杂调查。

### 11.2 何时才是硬上限

只有集成方控制完整请求、使用对应 tokenizer、能限制所有计费生成量、所有调用共用账本，
并在发出前预留最坏用量时，以上数字才可能兑现为硬 token 上限。
若模型把推理消耗记在可见输出之外，或适配器不能限制它，则 500 不是全部生成上限，
必须重新预算并明确为软限。不可观测/不可控制部分不能默认为零。

用户自带 AI 的情况下，RepoGc 默认只能限制案件数和交付材料范围：

- 宿主可能附带长对话、工具定义、重试或其他模型调用；RepoGc 不控制这些开销。
- 未取得宿主逐调用计量时，标为“实际用量未知；这里只是建议预算/交付文本估算”。
- 没有明确模型 tokenizer 时，只报字符/字节与估算假设，不把字符数当 token 数。
- 可计量部分显示“已知小计 + 未计量调用/阶段”，不能把小计叫总消耗。
- 账本导入只接收限定 run/session 的使用记录，不读取无关会话、不用账户额度百分比代替。

因此不应宣传“这个仓库跑一次只花 9,000 token”。本例的 858,009 个源码字符也不能直接
换算成账单。要先固定选中案件、完整请求、模型及使用环境，再做一次可观测的真实运行。

### 11.3 账本和金额

最小账本按 run/case/request/attempt/phase 记录：provider/model、输入/生成、缓存/推理
子集定义、成功/失败、来源、预算预留、缺失计量、时间和证据包摘要。生成量已含推理时
不能再加一次，输入已含缓存时也不能重复加；累计读数使用差值或最终有效记录，不逐条累加。
失败、重试、复核同样可能消耗 token。`reported / estimated / partial-known / unavailable`
四种状态分开；用户一次调查与产品开发/评估的消耗分账。

选定模型和计费规则后，金额按输入/生成/缓存各自的费率计算；费率未知时金额为未知。
保守预留可先不计缓存优惠：

`预算金额 = 输入预算 × 每百万输入费率 / 1,000,000 + 生成预算 × 每百万生成费率 / 1,000,000`

额外检索/工具服务费用另列。订阅中的 token 用量不等于用户实际新增账单。
本方案不假设任何当前模型价格，也不为了获得用量统计再接一个收费 Provider。
这轮设计及双子代理评审本身也用了 AI；没有逐调用收据，不能归并为“整体零 AI 成本”。

## 12. 准确性：同时评工程、AI 增益和整个流程

现在没有新方案的真实准确率。22 个属性案例只证明一个已知失败模式能被语法识别，
99 个现有单测通过也不证明新方案的精确率、召回率或用户收益。
AI 引用可校验、第二个 AI 同意，均不能作为意见正确的金标准。

### 12.1 最小对照试验

1. 开发集保留已知 22 例及第七节正反例；不把它们计入未知留出表现。
2. 另选 4 个未参与调规则的仓库，每仓分层随机抽取约 10 份 README/Skill/普通文档；
   纳入没有产生 Finding 的文件。没有相应文件类型就记录缺额，不伪造覆盖。
   同时从受支持代码文件抽取不依赖候选排名的补充样本；分层结果单列。
3. 两位评审不看系统结论，独立标注完整选中文件中的引用/名字观察，目标约 200 处；
   不只标扫描器找到的片段。至少一位最终裁定者是人；分歧可保留未知。
   若只有 AI 标注，则只能叫 AI 辅助初审，不声称具备可靠人工真值。
4. 冻结仓库提交、抽样规则、全量证据、支持范围、模型/提示词/预算后，同输入比较：
   旧工程、新工程、新工程加可选 AI。每仓同样最多 3 案，未被选中的真实问题仍计入漏检。
5. AI 路径重复三次，报告波动；重复不是三倍独立样本。自然真缺失不足时另做合成镜像
   注入测试，但真实/注入的准确性和占比分开，不能合并造出漂亮结果。
6. 冻结集一旦被用来调规则或提示词，就转为开发集；后续泛化要另找留出集。

该规模用于可行性判断，不足以证明通用准确率。按深查最大档估算，4 仓库 × 3 次 ×
33,000 = 396,000 token 的试验预算；不含另行使用的 AI 标注/裁判，若使用必须加账。
若只做初筛，则为 4 × 3 × 9,000 = 108,000。两者不是已经发生的用量，也不应计入单仓运行报价。

### 12.2 指标与分母

| 指标 | 定义与限制 |
| --- | --- |
| 工程确定覆盖率 | E/N，另列无法读取/解析文件；不是正确率 |
| 误报/精确率 | 最终缺失断言中，经独立真值确认的真缺失 / 全部该类断言；无断言时不适用 |
| 端到端召回 | 最终识别的真缺失 / 独立标注的受支持真缺失；包括从未被提取/派发的遗漏 |
| 弃判/范围外 | 单独报告，不算判断正确；进入覆盖统计，不混进精确率分母 |
| AI 派发 | 同时报观察数 A/N 与实际案件数/符合升级条件案件数，不混用单位 |
| AI 增益 | 比新工程单独运行多证实多少真问题、引入多少错误断言、减少多少未知 |
| 选择漏检 | 原文真问题在提取、工程判定、派发或展示哪一步丢失，逐项追踪 |
| 单位收益成本 | 每新增一个经核实的有效案件所用 token；没有增益时显示无收益，不报零成本 |

按仓库、语言、文件角色分层，同时展示计数、分母、区间/样本不足说明，避免一个大文件
决定总体表现。模型自己给出的置信度不是经过校准的准确率。

### 12.3 晋级条件与主要风险

- 确定性正反例、安全边界和注入真缺失全部通过；不以降低告警数替代这些检查。
- 冻结真实样本的新工程召回不能因过滤噪声无解释地下降；逐项审查新增漏检。
- 可以把“留出精确率至少 95%、支持范围内召回至少 90%”设为初期设计目标，
  不是已测结果、普遍保证或自动发布许可；正例/告警样本不足时明确无法判断是否达标。
  小样本的点估计不代表同等置信的总体准确率。
- AI 若把缺乏证据的猜测升级成确认结论，必须记为错误，不能因格式合法或复核者同意而放过。
- AI 必须相对工程单独运行有经核实的增益，且成本可接受；没有增益就保持默认关闭。
- 证据包缩小会遗漏反证；第二轮允许受控补充，预算耗尽则保留未知。增加 token 不保证更准。
- 工程选错候选会让 AI 看不到真正问题；必须审计未派发文件/观察，而不是只展示成功案例。
- 同模型的多次判断有共同盲点；独立复核用于找反证，不以多数票替代事实与人工裁定。

对外提 issue 仍是逐案单独检查：当前版本、具体用户影响、可复现证据、反证与重复讨论、
贡献政策及人类确认。总体准确率再高，也不能替代这道门。
