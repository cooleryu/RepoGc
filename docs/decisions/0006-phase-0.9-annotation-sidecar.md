# Decision 0006: Phase 0.9 optional annotation sidecar

- Status: Accepted
- Date: 2026-09-02
- Approval: `[human-approved 2026-09-02]`
- Change class: C — AI/mechanical boundary and report status semantics

## Context

RepoGC needs an optional background-story layer, but selecting a hosted model or
uploading repository snippets requires an explicit provider and data-handling
decision. Embedding a provider now would silently expand project authority and
privacy scope. Mixing generated text into the mechanical report would also make
it easier for AI language to be mistaken for deterministic evidence.

## Decision

Phase 0.9 implements a provider-neutral annotation sidecar protocol and validator.
RepoGC does not call a model or network service.

`repogc annotate` without an input exits successfully with an explicit skipped
status and writes nothing. With `--input`, it validates externally produced JSON
against an existing mechanical report. Valid output is printed to stdout or
written to an explicitly selected repository-relative sidecar path.

Each annotation must contain:

- an existing Finding ID;
- observed background;
- evidence-source paths present as existing, scanned Artifacts in the mechanical
  report;
- explicit uncertainties;
- human review checks.

The input must also record provider, model, and data-handling provenance. The
sidecar binds to a canonical JSON SHA-256 of the complete mechanical report.
Output is marked `ai_generated=true`, `human_verified=false`, and
`mechanical_report_modified=false`.

## Rejection rules

Validation fails when:

- the mechanical report is `UNRELIABLE`;
- the mechanical report Schema is absent or incompatible;
- the mechanical report contains duplicate Finding IDs;
- a Finding ID is missing, unknown, or duplicated;
- an evidence source is outside the report Artifact set;
- an annotation tries to add unsupported fields such as severity or verdict;
- required background, uncertainty, or human-check fields are empty;
- conservative English or Chinese deletion, retention, or value-verdict
  vocabulary appears;
- a requested sidecar would overwrite the mechanical report or its input.

The sidecar never modifies Findings, IDs, categories, evidence, strength,
reliability, graph data, trend, or baseline.

## Schemas and migration

- Annotation sidecar Schema starts at `0.1`.
- Mechanical report Schema changes from `0.5` to `0.6`.
- Mechanical reports expose `annotation_schema_version=0.1` and
  `ai_annotation_status=not_run` rather than claiming the feature is absent.
- Finding IDs and detector results do not change.
- The Schema change must trigger a trend-basis warning until the formal baseline
  is explicitly migrated.

## Deliberate omissions

- No built-in OpenAI or third-party Provider.
- No API key handling.
- No repository snippet selection or transmission.
- No automatic prompt execution.
- No merging sidecar prose into the mechanical report.
- No AI-generated Root, suppression, priority, severity, or Verdict.

Provider integration requires a separate decision stating what data is sent,
where it is retained, how it is disabled, and how offline operation remains
complete.

## Verification

- No-input annotation must skip with exit code zero and no output file.
- Valid input must leave the mechanical report byte-for-byte unchanged.
- English and Chinese deletion verdicts must be rejected.
- Unknown Findings, outside evidence paths, and reserved fields must be rejected.
- An `UNRELIABLE` report must be rejected.
- A1-A2 annotation sentinels and all existing regressions must pass.
- Wheel installation and no-write dogfood must remain functional.

## Rollback

Revert the Phase 0.9 implementation commit and explicitly restore or rebuild the
Schema 0.5 baseline. Sidecar files are separate artifacts and can be ignored by
older RepoGC versions; they must never be treated as mechanical reports.
