# Decision 0003: Phase 0.6 marker context

Status: Accepted
Authorization: `[human-approved 2026-09-02]`

## Problem

Phase 0.5 correctly separated strong path edges from contextual path mentions,
but `TODO`, `FIXME`, and Chinese unimplemented markers remained raw lexical
matches. On `best-runtime-box`, this produced 243 findings. Many were ordinary
lowercase uses of the product-domain word `todo`, test fixtures, source
strings, or historical state prose.

A raw marker count therefore repeated the original product failure: a
mechanically correct observation could still look like an actionable debt
count without evidence for that interpretation.

## Decision

Add deterministic marker context before human review. Every finding exposes:

- `evidence_kind`: the observed lexical or artifact context;
- `evidence_strength`: `review`, `contextual`, `strong`, or `candidate` as
  applicable to the finding category;
- `contract_sensitive`: whether the classified evidence occurs in an active
  configured contract context.

For marker findings, Phase 0.6 uses these defaults:

| Context | Evidence kind | Strength |
|---|---|---:|
| Source comment outside tests | `source_comment_marker` | review |
| Unchecked Markdown task | `unchecked_task_marker` | review |
| Contract or instruction prose | `contract_prose_marker` | review |
| Declared harness-state root prose | `operational_state_marker` | review |
| Test artifact | `test_marker` | contextual |
| Generated artifact | `generated_marker` | contextual |
| Source string or template literal | `string_literal_marker` | contextual |
| Fenced or inline code example | `fenced_example_marker` / `inline_code_marker` | contextual |
| Negated marker terminology | `marker_term_reference` | contextual |
| Ordinary documentation prose | `documentation_marker` | contextual |

`review` means that project-aware review is warranted. It does not mean the
work is unfinished, important, owned, safe to change, or related to repository
garbage.

## Deterministic language surface

- Python uses the standard-library tokenizer for comment versus string spans.
- JavaScript and TypeScript families use a conservative lexical state machine
  for line comments, block comments, quoted strings, and template literals.
- Shell uses a conservative lexical state machine for comments and strings.
- Markdown distinguishes fenced blocks, inline code, HTML comments, unchecked
  tasks, configured contracts, and declared harness-state roots.
- Test and generated roles override language syntax and remain contextual.
- ASCII marker tokens are matched exactly as configured. A configured `TODO`
  does not match lowercase `todo` or `todo-runtime`.
- Multiple markers on one line are all classified; the most review-relevant
  context represents the stable line finding.

## Schema migration

Report Schema changes from `0.2` to `0.3`. Finding IDs remain based on source
and normalized evidence, so adding context does not make line insertions change
identity. The formal baseline must disclose the schema and scanner-hash change
before explicit migration.

## Non-goals and limits

- no claim that a review-tier marker is an active requirement;
- no full JavaScript, TypeScript, or shell AST;
- no macro expansion, generated source-map analysis, blame ownership, or issue
  tracker reconciliation;
- no AI classification, scoring, suppression, automatic fix, or deletion;
- no inference from lowercase prose unless that exact token is configured.

Malformed or unsupported source remains scannable and is classified
conservatively. Coverage continues to report runtime, external, and business
meaning as not observed or not inferred.

## Verification

- preserve C1-C6 and G1-G2 sentinels;
- add G3 source-comment and G4 string-literal marker sentinels;
- cover Python, JavaScript/TypeScript-style, shell, Markdown, test, generated,
  contract, declared state, mixed same-line, and empty-marker cases;
- re-evaluate `best-runtime-box` in no-write mode and manually inspect every
  review-tier result;
- self-scan RepoGC and explicitly migrate the baseline.
